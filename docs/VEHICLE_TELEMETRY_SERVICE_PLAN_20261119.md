# 차량 데이터 서비스 분리 플랜

- 작성일: 2026-11-19
- 상태: 제안 플랜
- 대상: `dashboard/js` 차량 대시보드

## 목표

차량 값을 수신하고 디코딩·계산·보관하는 책임과 화면에 값을 표시하는 책임을 분리한다. 기존 값의 의미와 표시 동작을 유지하면서 UI가 데이터 수집 구현을 직접 호출하거나 소유하지 않도록 한다.

여기서 서비스는 앱 프로세스 안에서 사용하는 데이터 서비스 객체를 뜻한다. 화면이 보이지 않을 때도 계속 실행되는 Android `Service` 컴포넌트는 이번 범위에 포함하지 않는다.

## 현재 구조

- `DashboardActivity`가 `VehicleDataClient`를 만들고, `onResume()`에서 시작하며 `onPause()`에서 중지한다.
- `VehicleDataClient`가 OEM 리스너와 HSCAN/DCT 입력을 연결하지만, 콜백에서 `DashboardView`의 정적 메서드를 직접 호출한다.
- `DashboardView`가 정적 `Telemetry` 인스턴스를 소유하고, 수신 데이터 반영과 화면 렌더링 양쪽에 관여한다.
- 텔레메트리에는 프로필별 디코딩, 파생 계산, 최신 샘플·유효성·만료·이력 상태가 함께 있으므로 전환 중 해당 동작을 보존해야 한다.

## 목표 구조

- `VehicleTelemetryService`: `Telemetry` 상태를 소유하고 값 반영, 디코딩·계산 호출, 샘플과 이력 조회, 초기화 및 변경 통지를 담당한다.
- `VehicleDataClient` 및 HSCAN/DCT 입력부: OEM 구독과 원시 입력 수신을 맡고, 수신 결과를 `VehicleTelemetryService`에 전달한다. UI를 직접 참조하지 않는다.
- `DashboardView`와 렌더러: 서비스에서 받은 읽기 전용 스냅샷으로 화면을 그리고, 변경 통지를 받아 필요한 UI 갱신만 요청한다. 수신·디코딩·계산 API를 호출하지 않는다.
- `DashboardActivity`: 앱 프로세스 범위 서비스에 UI 관찰자를 연결하고 화면 재개 시 최신 스냅샷을 받는다. 화면 일시정지는 서비스 수집을 중지하지 않는다.

## 실행 단계

### 1. 입력 경로와 동작 기준선 확정

OEM 콜백, HSCAN, DCT, 수동·파생 계산 입력을 목록화하고 각 입력의 프로필 조건, 타임스탬프 기준, 유효성·만료·이력 동작을 기록한다. 현재 표시·진단 경로에서 `DashboardView`가 제공하는 데이터 접근 지점도 식별한다.

완료 기준: 모든 텔레메트리 쓰기 경로와 데이터 읽기 경로를 추적할 수 있고, 프로필별로 보존해야 할 동작이 명시돼 있다.

### 2. 서비스 API와 스냅샷 경계 추가

`VehicleTelemetryService`를 만들고 텔레메트리 상태를 서비스 소유로 이동한다. 수신 입력, 점화 상태 초기화, 프로필 설정, 샘플·이력·진단 조회를 서비스 API로 제공한다. UI용 스냅샷은 한 번에 일관된 상태를 읽을 수 있도록 구성하고, 변경 통지는 UI 스레드에서 안전하게 전달한다.

완료 기준: 서비스 단위에서 데이터 입력과 조회가 가능하고 `DashboardView`를 참조하지 않는다.

### 3. 수신부를 서비스에 연결

`VehicleDataClient`와 HSCAN/DCT 입력 콜백이 `DashboardView` 정적 메서드 대신 서비스에 입력을 전달하도록 전환한다. 세대 토큰, 지원 프로필 게이트, 재시도·리스너 해제 동작을 유지한다.

완료 기준: 차량 데이터 콜백에서 `DashboardView` 호출이 제거되고, 동일한 입력이 서비스 텔레메트리에 반영된다.

### 4. UI를 스냅샷 기반으로 전환

`DashboardView`가 소유한 정적 `Telemetry` 인스턴스와 데이터 쓰기용 정적 메서드를 제거한다. 렌더러·진단 화면이 서비스 스냅샷을 읽도록 바꾸고, 화면 갱신 통지는 기존 렌더링 스레드 규칙을 따른다.

완료 기준: UI 계층은 데이터를 직접 수신·디코딩·계산하지 않고, 기존 페이지·카드·그래프 표시가 유지된다.

### 5. 서비스 생명주기 연결

서비스는 Activity 필드에 종속되지 않도록 앱 프로세스 범위 소유자(예: `Application`)가 보유한다. 대시보드 데이터 세션이 처음 시작될 때 서비스를 시작하고, Activity는 화면 생명주기에 맞춰 UI 관찰자만 연결·해제한다. 서비스 중지는 `onPause()`나 `onStop()`에 연결하지 않고 데이터 세션이 명시적으로 끝날 때 수행한다. 프로세스가 살아 있는 동안 Activity가 잠시 가려지거나 재생성돼도 수집과 텔레메트리 상태를 유지한다.

| 시점 | 동작 |
| --- | --- |
| 앱의 대시보드 데이터 세션 시작 | 앱 범위 소유자가 `vehicleTelemetryService.start()`를 호출. 이 시점에 입력 클라이언트와 OEM/HSCAN 구독을 시작. 시작은 멱등적으로 처리. |
| `DashboardActivity.onCreate()` | 앱 범위 서비스 참조를 가져오고 UI를 구성. Activity가 데이터 수집 서비스의 소유자가 되지 않음. |
| `DashboardActivity.onResume()` | UI 관찰자를 등록하고 최신 스냅샷을 즉시 읽어 표시한 뒤 이후 변경을 반영. |
| 점화 상태 변경 | 서비스가 기존 정책대로 수신 게이트를 갱신하고 필요 데이터 상태를 초기화. UI가 관찰 중이면 갱신을 통지. |
| `DashboardActivity.onPause()` | UI 관찰자만 해제해 일시정지된 Activity에 갱신을 전달하지 않음. 텔레메트리 서비스, OEM/HSCAN 구독, 데이터 상태는 유지. |
| `DashboardActivity.onDestroy()` | 해당 Activity의 UI 관찰자만 해제. 서비스 종료나 데이터 초기화는 호출하지 않음. |
| 대시보드 데이터 세션의 명시적 종료 | 앱 범위 소유자가 `vehicleTelemetryService.stop()`을 호출해 리스너·재시도 콜백을 해제. |

완료 기준: Activity 재개마다 UI 관찰자는 하나만 등록되고, 일시정지 중 서비스는 계속 값을 수집하며 UI 콜백을 보내지 않는다. 재개하면 최신 스냅샷과 이후 변경을 표시한다. 명시적 데이터 세션 종료 후에는 구독과 재시도 콜백이 정리된다.

### 6. 회귀 검증 및 결과 기록

프로필별 입력·계산 결과, 샘플의 valid/stale/held 상태, 만료와 이력, 점화 초기화, 화면 갱신 통지, 시작·중지 반복을 검증한다. 가능한 호스트 테스트와 프로젝트 빌드 검사를 실행하고 결과를 구분해 기록한다.

완료 기준: 자동 검사 결과가 통과하고 기존 수신·표시 동작의 회귀가 없다. 호스트 검사만으로 OEM 서비스 응답이나 실차 동작을 확인했다고 간주하지 않는다.

## 범위와 검증 경계

- 기존 OEM API, 신호 매핑, 값 산식, UI 디자인은 이 플랜에서 변경 목표가 아니다.
- Android `Service` 컴포넌트, 별도 프로세스, OS 프로세스 종료 뒤 수집 자동 재개는 다루지 않는다.
- 프로세스 범위 서비스는 프로세스가 살아 있는 동안 Activity의 pause/stop/recreation과 독립적이다. OS 프로세스 종료 후에도 수집을 보장해야 한다면 Android `Service` 등 별도 실행·복구 설계가 필요하며 이는 추가 범위다.
- 구현 후 호스트 테스트와 실차/OEM 런타임 검증을 별도 증거로 보고한다.
- 현재 작업 트리에는 이 플랜과 무관한 수정 및 미추적 파일이 있으므로 구현 시 해당 변경을 보존하고, 이번 작업 파일만 선택적으로 수정한다.
